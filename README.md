# techdoc-rag

문서가 많은 조직에서 **"규정 어디에 뭐라고 적혀 있나"를 찾는 반복 업무**를 줄이는 문서 질의응답 시스템.

매뉴얼·약관·규정처럼 길고 표가 많은 문서를 대상으로, 질문을 받아 **근거 문서와 페이지를 붙여** 답한다. 근거를 찾지 못하면 답을 지어내지 않고 **찾지 못했다고 답한다.**

전 구간이 로컬에서 동작한다. 외부 API로 문서가 나가지 않는다.

```
질문: 인버터 설치 시 주위 온도 조건은?
답변: 인버터 설치 시 주위 온도는 -10~50℃입니다 [2].
근거: M100 사용설명서 p.12~18  (답변에 사용됨)
```

## 왜 이렇게 만들었나 — 감사·규제 관점

금융·보험처럼 **잘못된 답변이 곧 리스크인 영역**을 전제로 설계했다. 그래서 세 가지를 계약으로 못 박았다.

| 요구 | 이 시스템의 처리 |
|---|---|
| 답변의 출처를 댈 수 있어야 함 | 모든 답변에 `문서 / 버전 / 페이지 / 청크` 단위 근거를 붙임. **검색된 근거와 실제로 답변에 쓴 근거를 구분**해 표시 |
| 모르는 것을 지어내면 안 됨 | 근거를 못 찾으면 답변을 만들지 않음. 이유를 `관련 근거 없음 / 관련도 미달 / 근거 사용 미확인` 세 가지로 구분해 남김 |
| 장애를 품질 문제로 감추면 안 됨 | 검색 실패와 생성 실패를 서로 다른 예외로 분리. 검색이 실패했을 때 LLM의 일반 지식으로 우회하지 않음 |

같은 답을 두 번 냈을 때 왜 달라졌는지 추적할 수 있도록, 문서마다 **파서 버전 / 청킹 설정 버전 / 임베딩 모델 / 임베딩 버전 / 프롬프트 버전**을 함께 저장한다.

## 현재 상태

**파이프라인 전 구간 동작함.** 문서를 색인하면 화면에서 질문하고 근거와 함께 답을 받는다.

| 구간 | 상태 |
|---|---|
| 문서 등록 → 파싱 → 청킹 → 임베딩 → 색인 | 완료 |
| 질의 → 검색 → 근거 조립 → 생성 → 인용 | 완료 |
| HTTP API (`/chat`, `/health`) | 완료 |
| 화면 (Streamlit) | 완료 |
| 자동 테스트 | 196건 |
| **평가셋** | **미작성** — 아래 "아직 못 한 것" 참고 |
| 구조화 추출(UC-2), 문서 간 비교 | 설계만 |

## 실측

측정하지 않은 값은 성과로 쓰지 않는다. `[실측]`과 `[추정]`을 구분해 표기하고, 성능 수치에는 **측정한 장비명을 함께** 남긴다.

**대상 문서** — LS ELECTRIC 공개 인버터 매뉴얼 6권, 3,021페이지

| 항목 | 값 |
|---|---|
| 텍스트 추출 가능 | 97.8% (텍스트 레이어 없는 페이지 2.2%) |
| 문서 하나(270쪽) 색인 | 15초 / 205청크 (RTX 4060 노트북) |
| 표에서 온 청크 비율 | 70% (205개 중 143개) |

**응답 시간** — 같은 질문을 두 장비에서

| 장비 | 질의 임베딩 | 답변 생성 |
|---|---|---|
| RTX 4060 노트북 | — | 2~11초 |
| CPU 전용 노트북 (Core Ultra 7 155H) | 87ms | 8.0 tok/s |

**모델** — 임베딩 `bge-m3`(1024차원), 생성 `Qwen3.5 4B Q4_K_M`. 둘 다 Ollama로 서빙.

4B와 9B를 같은 조건에서 비교해 4B를 선택했다. 9B가 품질에서 앞설 여지는 있으나 **처리량이 1.7배 느렸고**(8.0 대 4.7 tok/s), 이 시스템의 병목이 생성 속도였다.

## 만들면서 확인한 것

기능을 붙이는 것보다 **틀린 답이 왜 나오는지 알아내는 데** 시간을 더 썼다. 대표 사례 하나.

> **증상** — "정격출력이 얼마에요?"라고 물었더니 정격 **전류** 값을 답했다.
>
> **가설 1: 표 인식 파서가 없어서.** 사양표가 한 줄 텍스트로 추출되어 항목과 값의 대응이 끊긴 것으로 보였다. 확인해 보니 표에서 온 청크가 전체의 70%였다.
> → **틀렸다.** 표 한 페이지에서 항목-값 10쌍을 뽑아 질문을 만들고 그 페이지만 근거로 주자 **9/10을 맞혔다.** 파서는 값을 제대로 뽑고 있었다.
>
> **가설 2: 검색이 엉뚱한 페이지를 가져와서.** 같은 뜻을 6가지로 물었더니 상위 3건 중 겹치는 것이 0~2건이었다.
> → **부분적으로만 맞았다.** 검색은 답이 있는 페이지 근처를 가져오고 있었다.
>
> **원인** — 1,200자 고정 분할이 정격표를 두 청크로 잘랐다. 값이 든 조각은 앞 페이지 본문과 섞여 유사도가 낮았고, 검색은 **값이 없는 뒤 조각**을 골랐다.
>
> **조치** — 검색으로 걸린 청크와 페이지가 겹치는 이웃을 근거에 함께 넣었다. 재색인 없이 답이 나오기 시작했다.

이 밖에 측정으로 뒤집힌 판단들.

- **`top_k`만 올린 것은 효과가 없었다.** 5→8로 늘려도 프롬프트에 들어간 근거는 5개 그대로였다. 근거 예산이 먼저 막고 있었다. 예산을 올리려고 토큰을 실측했다 — 이 문서는 한글 1자당 0.52토큰
- **질의 재작성은 켜지 않았다.** 구현과 테스트를 마쳤으나 응답이 평균 3.6초 늘고 근거 편차는 줄지 않았다. 정답 라벨이 없어 품질 개선을 판정할 수 없으므로 기본값을 끈 채 두었다
- **Elasticsearch를 검토하고 도입하지 않았다.** 한국어 형태소 분석(Nori)이 매력적이었으나, 저장소가 둘이 되고 라이선스 검토가 필요했다. 무엇보다 "동시 사용자가 늘면 검색이 병목"이라는 가정을 재보니 **검색 87ms 대 생성 5~11초**로 병목은 생성이었다

판단 과정과 버린 대안은 별도 저장소의 결정 기록에 남긴다.

## 구성

```
운영자 ──> 색인 서비스 ──> PDF 파서 ──> 청커 ──> 임베딩 ──> Qdrant(벡터)
                  └──> SQLite (문서 생명주기·재현성 메타)

사용자 ──> Streamlit ──> FastAPI ──> 질의 서비스 ──> 검색(Qdrant + 활성 문서 필터)
                                          └──> 근거 조립 ──> Ollama ──> 답변 + 근거
```

운영자가 문서를 미리 등록하고 사용자는 준비된 지식기반에 질의한다. 사용자 업로드는 범위에 없다.

| 계층 | 선택 | 이유 |
|---|---|---|
| 화면 | Streamlit | 데모·검증용. 프런트엔드는 이 프로젝트의 관심사가 아님 |
| API | FastAPI | 화면과 평가 스크립트가 같은 입구를 쓰게 함 |
| 벡터 저장소 | Qdrant | 메타데이터 필터와 영속성. 로컬 파일 모드로 시작 |
| 문서 장부 | SQLite | 문서 상태·버전·소유권의 정본 |
| 파서 | pypdfium2 | BSD/Apache. PyMuPDF는 AGPL이라 배제 |
| 모델 서빙 | Ollama | 로컬 실행 |

**교체 가능하게 두었다.** LLM·임베딩·벡터 저장소는 인터페이스 뒤에 있고, 서비스 계층은 구현체를 모른다. 모델을 바꾸려면 어댑터 하나와 설정 한 줄만 바뀐다.

**운영에서 걸리는 것들을 코드에 반영했다.** 동시 생성 수 제한(세마포어), 대기·생성 타임아웃 분리, HTTP 커넥션 재사용, 스트리밍 취소 시 커넥션 폐기, 색인 중단 감지(heartbeat·리스), 재색인 시 고아 벡터 정리, 인덱스 별칭 전환.

## 실행

Ollama가 먼저 떠 있어야 한다.

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[dev]"

# 1) 매뉴얼 색인
.venv\Scripts\python.exe scripts\verify_ingestion_real.py --pdf <매뉴얼.pdf>

# 2) API — 127.0.0.1에만 연다. 인증이 없으므로 외부에 노출하지 않음
.venv\Scripts\python.exe -m uvicorn --factory techdoc_rag.api.app:create_default_app \
    --host 127.0.0.1 --port 8000 --app-dir src

# 3) 화면 (다른 터미널에서)
.venv\Scripts\python.exe scripts\run_ui.py
```

화면은 `scripts/run_ui.py`로 띄운다. 주소가 스크립트에 박혀 있어 실행 위치나 명령 실수와 무관하게 `127.0.0.1`에만 열린다. Streamlit을 직접 실행하려면 `--server.address=127.0.0.1`을 반드시 붙일 것 — 설정 파일은 **실행 디렉터리 기준**으로 읽히므로 저장소 밖에서 띄우면 기본값 `0.0.0.0`으로 되돌아간다.

변경 전후 답변 비교는 `scripts/probe_answers.py`로 한다.

## 아직 못 한 것

정직하게 적는다. 이 목록이 다음 작업 순서이기도 하다.

- **평가셋이 없다.** 정답 라벨이 없으므로 정확도를 숫자로 말할 수 없다. 공개 Q&A 게시판의 실제 질문을 수집해 `(문서, 페이지)` 단위로 라벨링할 계획이다. 질문을 직접 지어내면 시스템이 잘 푸는 것만 만들게 되어 평가가 편향된다
- **하이브리드 검색 미적용.** 모델번호·파라미터 코드 같은 정확한 문자열 질의는 의미 검색이 놓치기 쉽다. 한국어 형태소 처리 확인이 선행 과제다
- **표의 계층 구조가 사라진다.** 그룹 머리글과 하위 행의 관계가 텍스트 추출에서 유실된다
- **구조화 추출(UC-2)과 문서 간 비교는 설계만** 되어 있다
- **모니터링·로깅이 최소 수준**이다. 질의 로그는 원문을 저장하지 않고 지연·모델·검색 건수만 남기도록 설계했으나 대시보드는 없다

## 대상 문서와 저작권

LS ELECTRIC이 공개한 저압 드라이브(인버터) 국문 매뉴얼을 사용한다. 평가 질문은 같은 제조사의 공개 Q&A 게시판에 올라온 실제 질문에서 수집한다.

**매뉴얼과 게시글의 저작권은 각 권리자에게 있다. 이 저장소는 원문을 포함하지 않는다.** 파일명·페이지·출처 URL만 기록하고 원문은 스크립트로 각자 내려받는다.

이 시스템은 **단일 장비에서 개인이 실험·평가 목적으로 실행하는 것을 전제**로 한다. 수집한 자료를 재배포하거나 공개 서비스로 배포하지 않는다.
