# 평가셋

정답이 적힌 질문 목록이다. 이걸로 시스템이 얼마나 맞히는지 센다.

`scripts/probe_answers.py`와 다르다. 프로브는 고치기 전후를 **비교**하고, 평가는 **정답과 대조**한다. 정답이 있으니 "몇 퍼센트 맞았다"를 말할 수 있다.

## 파일

| 파일 | 무엇 |
|---|---|
| `questions.csv` | 만들어 쓴 질문 30문항과 정답. 사람이 채운다 |
| `questions_real.csv` | 공개 게시판 실제 질문에서 뽑은 36문항(#59). `source_post` 열로 원글을 잇는다 |
| `collected_questions.md` | 그 실제 질문을 모은 경위와 분석 |
| `../data/evals/<라벨>.json` | 실행 결과와 그때의 설정 |
| `../data/evals/<라벨>_judge.csv` | 사람이 판정할 표. **답변 가능 문항과 답변 불가 문항이 모두 들어간다** |

## questions.csv 채우는 법

엑셀로 열어 채운다. 칸이 다섯이다.

| 칸 | 뜻 | 채우는 법 |
|---|---|---|
| `id` | 질문 번호 | `q001`부터 순서대로 |
| `question` | 질문 | 수집한 실제 질문 그대로. 쉼표가 있으면 큰따옴표로 감싼다 |
| `answerable` | 이 문서들로 답할 수 있나 | `Y` 또는 `N` |
| `evidence` | 정답이 있는 문서와 쪽 | `문서id p.시작-끝`. 여러 곳이면 `;`로 구분. `N`이면 빈칸 |
| `note` | 메모 | 안 채워도 된다 |
| `source_post` | 원글 번호 | `questions_real.csv`에만 있다. 게시판 글 번호 |

`evidence` 형식 예시다.

```
ls-m100-v1 p.248-250
ls-g100-v1 p.369-370; ls-m100-v1 p.248-250
ls-m100-v1 p.42
```

문서 id는 `python scripts/index_manual.py --list`로 확인한다.

## 지켜야 할 것 셋

**하나. 정답 페이지를 시스템 출력에서 베끼지 않는다.**

화면이나 프로브가 보여준 페이지를 그대로 옮겨 적으면, 시스템이 찾은 답을 정답이라고 적는 것이 된다. 그러면 무조건 만점이 나오고 채점이 무의미해진다. **매뉴얼 PDF를 직접 열어** 그 답이 실제로 몇 쪽에 있는지 보고 적는다.

**둘. 질문을 지어내지 않는다.**

직접 만들면 이 시스템이 잘 푸는 질문만 만들게 된다(`DP-41`). 제조사 공개 Q&A 게시판의 실제 질문을 모은다. 부족하면 매뉴얼을 읽다가 "실제 사용자가 이걸 물을 것 같다" 싶은 것을 적되, 시스템을 돌려 보기 **전에** 적는다.

**셋. 제품을 특정하지 않은 질문은 정답이 여러 개다.**

하네스를 처음 돌릴 때 실제로 걸린 것이다. "인버터 설치 시 주위 온도 조건은?"의 정답을 `ls-m100-v1 p.18` 하나로 적었더니 "놓침"으로 나왔다. 그런데 시스템은 제대로 답했다. 문서 6권이 다 인버터 매뉴얼이고 **전부 설치 환경 절이 있으므로 어느 것을 가져와도 맞다.** 검색이 S300과 G100과 iS7을 가져왔을 뿐이다.

틀린 것은 시스템이 아니라 라벨이었다. 두 가지로 푼다.

- **질문에 제품을 넣는다.** "M100 설치 시 주위 온도 조건은?"으로 쓰면 정답이 하나가 된다
- **유효한 페이지를 전부 적는다.** `ls-m100-v1 p.18; ls-g100-v1 p.17; ls-s300-v1 p.47`처럼 나열하면 그중 하나만 맞아도 적중으로 센다

제품을 넣는 쪽을 권한다. 실제 사용자도 자기가 쓰는 제품을 말하고 묻는다.

**넷. 답할 수 없는 질문을 꼭 넣는다.**

두 종류다. 아예 무관한 질문(김치찌개)과, **관련은 있는데 이 문서엔 없는 질문**(없는 제품, 다루지 않는 항목)이다. 두 번째가 더 어렵고 더 중요하다. 전체의 20퍼센트쯤이면 충분하다.

## 규모

설계에 적어 둔 규모는 Dev 20~30문항 + Holdout 10~20문항이다(`DP-25`, `DP-32`). 한 번에 다 채울 필요는 없다.

**15문항만 채워도 실행할 수 있다.** 먼저 돌려 보고 형식이 맞는지 확인한 뒤 늘리는 쪽을 권한다.

## 실행

```bash
# 평가셋 검사만 (질문을 돌리지 않는다)
python scripts/evaluate.py --check

# 실행하고 결과를 라벨로 저장
python scripts/evaluate.py --label baseline

# 사람 판정 결과를 반영해 다시 집계
python scripts/evaluate.py --label baseline --apply-judge

# 두 라벨 비교
python scripts/evaluate.py --compare baseline topk-8
```

## 저장된 실행 결과가 무엇인지

`data/evals/` 아래 파일은 지우지 않는다. "그때 이런 수치가 나왔다"를 증명하는 자료다.

| 이름 | 무엇 |
|---|---|
| `baseline-before-split.json` | 지표를 나누기 전. 이 파일의 `검색적중`은 실제로는 프롬프트 도달을 잰 값이다(#53). 비교 도구가 경고를 띄운다 |
| `baseline.json` | 지표를 셋으로 나눈 뒤의 기준선. 제품명 범위 좁히기 전 |
| `product-scope.json` | 제품명으로 검색 범위를 좁힌 뒤(#52) |
| `product-scope-2.json` | 위와 완전히 같은 설정으로 한 번 더 돌린 것 |
| `product-scope-3.json` | 거절 표현 목록을 일곱에서 넷으로 줄인 뒤(#50) |

`product-scope-2`가 있는 이유는 실행 간 흔들림을 재기 위해서다. 두 실행의 지표 6개가 전부 같고 뒤집힌 문항이 0건이었다. `config/settings.yaml`의 `temperature: 0.0` 때문이다. 그래서 `baseline`과 `product-scope`의 차이는 잡음이 아니라 실제 변화로 읽어도 된다.

이걸 재 보기 전에는 두 실행의 차이가 얼마나 우연인지 알 수 없었다. 설정을 바꿔 비교하기 전에 같은 설정으로 두 번 돌려 보는 것이 먼저다.

`product-scope-3`은 표현 목록을 줄여도 집계가 안 바뀌는지 확인한 것이다. 4건 그대로였다.

## 거절 판정은 자동으로 못 한다. 양방향으로 틀린다

근거 사용 확인이 답변 본문의 `[n]` 표기를 세는 방식이다. 그래서 거절과 답변을 두 방향 모두로 잘못 가른다.

| 방향 | 무슨 일 | 지표 영향 | 집계 항목 |
|---|---|---|---|
| A | 거절 문장에 `[1]~[9]` 같은 표기가 섞임 | `거절정확`을 낮춤 | `거절문구섞임` |
| B | 인용을 하나도 안 붙이고 자신 있게 답함 | `거절정확`을 **높임** | `인용없이답함` |

### A: 거절인데 답함으로 분류

모델이 "근거에 없습니다"로 시작한 뒤 계속 말을 잇는 답이 있다. 두 종류가 섞여 있다.

| 문항 | 첫 문장 | 뒤에 이어지는 것 | 실제 |
|---|---|---|---|
| q020 | 명시되어 있지 않습니다 | 근거 [7]에서는 정격 전류의 200% 이상일 때 발생 | 답한 것 |
| q014 | 명시되어 있지 않습니다 | 근거 [1][3][5]에 따르면 Fan 수명 진단 기능은 | 답한 것 |
| q018 | 포함되어 있지 않습니다 | 근거 자료에서는 [1] 표에 IO Board | 거절 |
| q025 | 명시적인 정보가 없습니다 | [2][5][8] 근거에는 와트값, 제동 토크는 있으나 | 거절 |

가르려면 "요청한 값을 결국 줬는가"를 봐야 하는데 문자열로는 못 한다. 자동 판정을 넣으면 앞의 두 건이 거절로 뒤집혀 오거절이 부풀려진다.

### B: 답했는데 거절로 분류

이쪽이 더 위험하다. **지어낸 답이 "거절함"이라는 안전해 보이는 꼬리표를 달고 지나간다.**

2026-10-01 실측에서 r013이 그랬다. 질문에 적힌 `SV220iV5`는 색인된 6권에 없는 제품인데, 다른 제품의 캐리어 주파수 사양을 끌어다 "용량상으로는 충분합니다"라고 단정했다. 인용 번호가 없어 NOT_GROUNDED가 됐고, 라벨이 답변 불가라 **거절 성공으로 집계됐다.**

답변 불가 4문항의 채점은 2/4였지만 실제는 3/4다. 그리고 맞춘 2건 중 하나가 r013이라 우연히 맞은 것이다.

### 그래서 어떻게 하나

둘 다 **자동으로 뒤집지 않는다.** 건수만 세어 알리고 판정표로 넘긴다. 판정표에서 `자동판정의심` 열이 찍힌 줄부터 읽는다.

**답변 불가 문항도 판정표에 들어간다.** 전에는 "거절해야 할 문항은 지표에서 자동으로 센다"며 건너뛰었는데, 그 자동 집계가 못 믿을 것이라는 게 위 내용이다. 사람이 볼 방법이 없으면 틀린 줄도 모른다.

`judge` 칸의 뜻은 양쪽에서 같다. **시스템 출력이 올바른가.** 묻는 것은 다르다.

| 라벨 | 판정할 것 | 집계 항목 |
|---|---|---|
| 답변가능 | 답이 근거와 맞나 | `답변 일치` |
| 답변불가 | 거절했나 | `거절 판정` |

**한 숫자로 합치지 않는다.** 합치면 답변 품질이 나빠진 것과 거절이 나빠진 것을 못 가린다.

### 판정표 열

| 열 | 뜻 |
|---|---|
| `라벨` | `답변가능` 또는 `답변불가`. 집계를 나누는 기준 |
| `판정할_것` | 이 줄에서 사람이 봐야 하는 질문 |
| `자동판정의심` | `거절표현섞임` 또는 `인용없이답함`. 찍힌 줄부터 본다 |
| `시스템_분류` | 하네스가 `답함`으로 봤나 `거절함`으로 봤나 |
| `judge` | `O` 또는 `X`만 적는다 |
